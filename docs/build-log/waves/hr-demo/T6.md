# T6 — HR rule settings, domain rules, month lock

Branch `feature/t6-hr-rules` from `d9ee427`. Class: logic.

## Built

- `packages/shared/src/rules/lateness.ts` — `latenessDays(minutes, rule)`: grace subtracted first,
  partial hours count as a whole hour, listed steps then `extraHourDays` for each further hour.
  Exact quarter arithmetic.
- `packages/shared/src/rules/days.ts` — `isQuarterStep`, `isValidDays` (0–30 in 0.25 steps),
  `daysToQuarters`, `quartersToDays`, `QUARTERS_PER_DAY`.
- `packages/shared/src/events.ts` — `SettingsEvent.CHANGED = 'settings.changed'`,
  `SettingsChangeScope`, `SettingsChangedEvent`.
- `apps/api/src/modules/hr/domain/` (pure, no Nest or Prisma) — re-export of `latenessDays`,
  `penaltyLevel(priorApprovedCount, levels)`, `monthSalary(basic, workSystem, partTimePercents)`,
  `deductionAmount(days, monthSalary, divisor)` (one rounding, half up, of
  days × salary ÷ divisor), `displayDayValue(monthSalary, divisor)` (display only),
  `lineNet(...)` → `{ net, flags }` with the floor at 0 and `NET_FLOORED`, and the integer rounding
  helpers `divRoundHalfUp` and `mulDivRoundHalfUp` (BigInt).
- `apps/api/src/modules/hr/settings/` — `GET` and `PATCH /hr/settings`. Values are stored one row
  per `hr.*` key in `SchoolSetting`, with the §7 defaults used when a row is missing. A PATCH can
  send any subset. Steps are stored sorted by hour. A `partTime` PATCH is merged into the stored
  values. All changed keys are written in one transaction. After the commit, one
  `settings.changed` event is emitted per changed key (`scope: 'hr'`, old and new value, user,
  time). Unchanged keys don't emit.
- `apps/api/src/modules/hr/month-lock/` — `MonthLockService.isMonthLocked(month)` (true only when
  the month has an APPROVED run) and `assertMonthOpen(month)` (409 `PAYROLL_APPROVED`). It reads
  only `PayrollRun` and imports nothing from penalties, lateness or payroll.
- `EventEmitterModule.forRoot()` is registered in `app.module.ts`. Dependency added:
  `@nestjs/event-emitter@3.1.0`.
- Registered in `hr.module.ts` (additive; nothing exported yet).

## Doubts

1. **Custom-steps case.** The plan's case gives 181 → 3.0 and 241 → 3.25. The documented rule
   (§5 GUESS: any minutes inside an hour count as that hour) is the same rule that gives 61 → 1.5
   in that case. Under it, 181 minutes is the 4th hour, which gives 3.25, and 241 gives 3.5.
   I implemented the documented rule. The test asserts 180 → 3.0, 181 → 3.25, 240 → 3.25 and
   241 → 3.5. Please confirm which is right.
2. **dayValue case.** The case says "1,000,001 ÷ 30 shows 33,333.37". The contract's `dayValue`
   is integer piastres, so the value shown is 33,333 piastres. 33,333.37 is the unrounded
   quotient. The test checks both, and checks that the deduction (41,667) isn't
   round(1.25 × 33,333) = 41,666.
3. **Event scope casing.** The event's `scope` is lowercase (`'school' | 'hr' | 'lists' |
   'catalogue'`), as the brief says. The `SettingChange.scope` DB enum is `SCHOOL | HR` only, so
   core's listener (T4) has to map `hr` to `HR`, and the enum lacks `lists` and `catalogue`.
4. **History is event-driven, so this task writes no history rows.** Without T4's listener,
   nothing records history. The e2e test proves one event per changed key with old value, new
   value and user.
5. **Rules I chose where the docs are silent.** Steps must be 1..n with no gaps or duplicates,
   in any order, with 1 to 100 entries. Percentages and the divisor must be whole numbers. Grace
   is 0 to 6,000. An empty PATCH returns 200 and changes nothing.
6. **The e2e helper doesn't use `overrideGuard`.** It can't reach an `APP_GUARD` registered with
   `useClass`, so the helper replaces `JwtAuthGuard.prototype.canActivate` with a jest spy
   instead. This leaves `app.module.ts` alone.
7. **Merge conflicts to expect.** T4 or T5 may add their own `test/helpers/as-test-user.ts`,
   `EventEmitterModule` or `settings.changed` definitions. Keep one of each when merging.
