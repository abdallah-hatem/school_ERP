# T7 — Penalty catalogue and records

Branch `feature/t7-penalties` from `f36a72f`, rebased on `origin/dev` (with T4 and T8). Class: logic.

## Built

- `apps/api/src/modules/hr/penalties/`
  - Catalogue (`PenaltyCatalogueController`, `PenaltyCatalogueService`,
    `PenaltyCatalogueRepository`): `GET /hr/penalty-groups` (all groups with violations and
    levels, retired ones included with `isActive`), `POST /hr/penalty-groups`,
    `PATCH /hr/penalty-groups/:id`, `POST /hr/penalty-groups/:groupId/violations`,
    `PATCH /hr/violations/:id`. There are no DELETE routes. Levels are replaced as a whole when
    they are edited. Every create and every real change emits `settings.changed` with scope
    `catalogue` after the write. Keys are `hr.penaltyGroups` and `hr.violations`, and the old and
    new values are snapshots. Core's listener writes the history row, and the e2e test checks
    that row.
  - Records (`PenaltiesController`, `PenaltyRecordsService`, `PenaltyRecordsRepository`):
    `GET /hr/penalties` (paginated; filters are `employeeId`, `month`, `status`, and `search`
    over the employee code and names and the violation names), `GET /hr/penalties/preview`,
    `GET /hr/penalties/:id`, `POST /hr/penalties`, `POST /hr/penalties/:id/approve` and
    `POST /hr/penalties/:id/cancel`. There is no DELETE route.
  - Level = 1 + the APPROVED records for the same employee and violation whose date is in
    `[windowStart, date)`. After the last level, the last level repeats. The window comes from
    `HrSettingsService.get()`. A PENDING record is shown with the count and catalogue as they are
    today, and a whole page is computed in one query. Approval computes the level again and then
    stores `level`, `action` and `days` for good. APPROVED and CANCELLED records always show their
    stored values.
  - Approval runs in a transaction. It takes a `pg_advisory_xact_lock` on (employee, violation)
    and then makes a conditional update `where status = PENDING`. Two approvals can't both read
    the same count, and approving the same record twice gives exactly one 200 (this is tested).
    Cancelling is also a conditional update (PENDING or APPROVED → CANCELLED). Cancelling never
    recomputes any other record.
  - Errors: unknown employee or violation in the body → 400 `FOREIGN_KEY_VIOLATION`. Inactive
    employee → 409 `EMPLOYEE_INACTIVE` (through T8's `EmployeesService.assertActive`). Retired
    violation, or a violation in a retired group → 400 `VIOLATION_RETIRED`. A future date or a bad
    date → 400. Invalid levels → 400 `INVALID_LEVELS`. Approving an APPROVED record → 409
    `PENALTY_NOT_PENDING`. Acting on a CANCELLED record → 409 `PENALTY_CANCELLED`. Recording,
    approving or cancelling in a month whose payroll is approved → 409 `PAYROLL_APPROVED`
    (`MonthLockService.assertMonthOpen`). A cancel without a reason → 400.
- `hr/domain/penalties.ts` (extended): `repetitionWindowStart`, `countPriorInWindow` and
  `resolvePenalty`. All three are pure and unit tested.
- Registered in `hr.module.ts` (additive). Nothing new is exported. T9 is in the same module and
  can inject `PenaltyRecordsService`, or read `penalty_records` (APPROVED, `days`, `date`)
  directly.

## Edge cases (24/24, each has an e2e test named after it)

The T7 list has 10 cases and the review section has 14. The 3 Nov / 10 Nov case passes in its
corrected order: 1, 2 one way and 1, 1 the other way. Records on the same date both get level 1.
There are also 4 extra tests: a full flow, concurrent approvals, unknown ids, and approve or
cancel of an APPROVED record in a locked month. Unit tests cover the shared rule, the domain
window functions and both services.

## Doubts

1. **ROLLING_12_MONTHS boundary.** The window starts on the same day 12 months earlier, and that
   day counts. So an approval on 2025-11-17 counts on 2026-11-17. The review case only fixes
   11-16 (counts) and 11-18 (doesn't count). 29 Feb goes back to 28 Feb.
2. **Retired group.** I treat a violation inside a retired group as retired too
   (`VIOLATION_RETIRED`). The docs only talk about retired violations.
3. **Approving a PENDING record whose violation was retired, or whose employee was deactivated,
   after it was recorded** is allowed. The rules only block new penalties. The catalogue levels
   used are the ones in place today.
4. **Investigation days.** If days are given, they must be > 0. 0 is rejected rather than read
   as "no days".
5. **Approval race with payroll approval.** The month lock is checked before the transaction,
   the same way T8 does it.
6. **Preview** doesn't check the month lock. The contract says nothing is saved, so the screen
   can still show the level.
7. `INVALID_LEVELS` is also used for day problems inside levels, such as a NOTICE with days. The
   locale message only mentions numbering, so T12 may want a broader wording.
