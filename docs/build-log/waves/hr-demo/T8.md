# T8 — Monthly lateness

Branch `feature/t8-lateness` from `f36a72f`, rebased on `origin/dev`. Class: logic.

## Built

- `apps/api/src/modules/hr/staff-attendance/` — `GET /hr/lateness?month=YYYY-MM` and
  `PUT /hr/lateness/:month` (`{ entries: [{ employeeId, minutes }] }`).
  - GET lists every ACTIVE employee (by code) as `{ employee: { id, code, nameEn, nameAr },
    minutes, days }`. Minutes are 0 when nothing is stored. `days` is never stored. It comes from
    `latenessDays` (shared rules, via `hr/domain`) with the current rule from
    `HrSettingsService.get()`, so a rule change shows up on the next read.
  - PUT checks `MonthLockService.assertMonthOpen` first (409 `PAYROLL_APPROVED`), then the
    employees (unknown → 400 `FOREIGN_KEY_VIOLATION`, inactive → 409 `EMPLOYEE_INACTIVE`). Then it
    upserts only the given entries in one transaction, recording `updatedById` from
    `@CurrentUser`, and returns the month's list. Employees left out keep their stored value. An
    empty `entries` array writes nothing.
  - Validation: month `YYYY-MM` (400). Minutes must be a whole number from 0 to
    `SETTING_LIMITS.latenessMinutesMax` (6,000) (400). `employeeId` must be a UUID. A duplicate
    `employeeId` in the body → 400 (`@ArrayUnique`).
- `EmployeesService` (T5, extended additively): `listActiveRefs()` and `assertActive(ids)`.
  `EmployeesRepository` gains `findActiveRefs()` and `findStates(ids)`.
- Registered in `hr.module.ts` (additive). Nothing new exported. T9 can export `LatenessService`
  or read the table when it needs the minutes.

## Edge cases (7/7 have an e2e test named after the case)

T8 list (5): minutes negative, decimal or above 6,000; inactive employee; approved month; days
follow the current rule; bad month format. Review section (2): 6,000 / 6,001 / 0; duplicate,
unknown and left-out employees. There is also one full-flow test, plus unit tests for
`LatenessService`, `assertActive` and `isMonth`.

## Doubts

1. **No pagination on GET.** The contract returns the whole month's list, and the screen needs
   every active employee at once, so the list isn't paginated. The house rule says lists are
   paginated. Revisit if headcount grows large.
2. **Which code for an unknown employee?** I used `FOREIGN_KEY_VIOLATION` (400), as T5 does for
   unknown list ids. There is no dedicated code.
3. **Approval race.** The lock is checked just before the write, not inside the same transaction.
   An approval that lands between the check and the write could let one PUT through. That is
   acceptable for the demo. T9 could take a row lock if it matters.
4. **Inactive employees' stored minutes** stay in the table but are hidden from GET (the contract
   says active employees only).
