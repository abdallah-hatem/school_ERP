# T16 — Seed data

Branch `feature/t16-seed` from `98c6da8`, rebased on `origin/dev`. Class: logic.

## Built

- `apps/api/prisma/seed/run.ts` — `runSeed()` boots the real `AppModule` as a Nest application
  context and writes everything through the owning services, never with raw inserts:
  - the HR admin (T2's `seedAdmin`, unchanged)
  - school identity and logo (`SettingsService.setValues` / `setLogo`, so the logo goes through
    the upload checks and file storage and is served at `/files/logo/…`). Every other setting
    keeps its §7 default, because a missing row means the default.
  - stages, departments and job titles (`StagesService`, `DepartmentsService`, `JobTitlesService`)
  - 40 employees (`EmployeesService.create` / `deactivate`)
  - the catalogue (`PenaltyCatalogueService`)
  - November 2026 lateness (`LatenessService.put`)
  - penalties, created then approved or cancelled through `PenaltyRecordsService` in date order,
    so the service computes the levels
  - the DRAFT run and its 2 adjustments (`PayrollService`)
- Idempotent. Every item is matched on a natural key: list and group names, national ID,
  violation + employee + date, and the run's month. Only what is missing is created, so a second
  run creates nothing and uses no employee codes. When the run already exists it is
  recalculated. Once the month's payroll is approved, the month's data is left alone.
- Catalogue updates (second commit). A group or violation that already exists, matched by
  English name, is updated through `PenaltyCatalogueService` when its Arabic name, note or
  levels differ from the data. Each update writes a history row. Approved penalties keep their
  fixed levels.
- Data:
  - `prisma/seed/data/` (tracked) holds the generic lists, 40 fake employees (Egyptian names in
    EN/AR, all four stages, all four work systems, EGP 5,000–20,000, managers, 2 inactive), the
    November plan (15 lateness entries of 0–200 min; 11 penalties: 8 approved, 2 pending,
    1 cancelled; employee 14 reaches level 3 and employee 16 level 2 plus a pending third) and
    the fallback ("School ERP Demo" / "مدرسة تجريبية", no logo, 4 groups, 7 violations).
  - `prisma/seed-data.local/` (git-ignored) holds `school.json`, `catalogue.json` (4 tables,
    72 violations) and `logo.png`. The loader uses this folder when it is present and the
    fallback otherwise. It validates levels with the shared `violationLevelsProblem` and requires
    the six `seedKey`s that the demo penalties use. `SEED_DATA_DIR` can point the loader at
    another folder.
- `db:seed` and the prisma seed command now run with `ts-node --transpile-only` instead of
  `tsx`, because esbuild doesn't emit the decorator metadata that Nest's injection needs.

## Edge cases (5/5, `apps/api/test/seed.e2e-spec.ts`)

- [x] Seed run twice → no duplicate employees or admin; codes not reused
- [x] Seeded catalogue = 4 groups, 72 violations, each with 1–5 gap-free levels; DEDUCT_DAYS levels have days > 0
  (72 with the local data; with the fallback, the fallback's own count)
- [x] Seeded repeated penalties carry the levels `penaltyLevel()` gives over earlier approved ones
- [x] The seeded November run recalculates with penalty, lateness and adjustment lines, and PENDING_PENALTIES where penalties are pending (approve → `PENDING_PENALTIES`)
- [x] No credentials or client catalogue text in tracked files. The test checks that nothing
  from `seed-data.local/`, no `.env`, no `*.local.md` and no `CREDENTIALS` file is tracked. It
  also searches every tracked text file for the school's names, each Arabic violation name, and
  each English violation name of 30 characters or more. Shorter English phrases are skipped
  because they are generic: a T12 web test fixture uses "Using a phone in class".
- plus a full-flow test, and a test that re-seeding after the catalogue data changed updates a
  group and a violation in place without creating anything. The suite passes with the local data and with the fallback
  (`SEED_DATA_DIR` pointed at an empty folder).

## Doubts

- The Arabic group and violation names in `seed-data.local/catalogue.json` are transcribed
  word for word from the scanned booklet pages (p19–p25). Sub-case items use the general wording.
  Two sets of levels were corrected from the scan:
  - A-18: 1 / 2 / 4 days, with loss of half the raise added to level 3.
  - B-9: investigation with 2 days at levels 1–3, then dismissal.
- A regulation level that combines two actions (e.g. "5 days + warning", "3 days + loss of half
  the raise") is stored as its main action (the day deduction). The rest goes in the
  violation's note, because the schema has one action per level.
- Some items are a single regulation number with sub-cases (A-10, A-26, A-38). Each is stored as
  one violation with the general case's levels, and the other case goes in the note. "Delayed
  promotion" (B-2, level 2) has no action of its own, so it is mapped to `RAISE_DEFER_3M` and
  noted.
- "3–4 days" (A-8, level 3) is stored as 3 days.
- If the catalogue was first seeded from the fallback and the local data is added later, both
  catalogues end up in the database, because the seed only adds and never retires.
