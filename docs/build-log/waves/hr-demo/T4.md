# T4 — Core settings and school structure (backend · logic)

Branch `feature/t4-core-settings`, rebased on `dev` after T6 (#6) and T5 (#7).

## Built

- `core/settings`
  - `GET/PATCH /settings/school`. Typed values are stored one row per key in `SchoolSetting`, with the
    §7 defaults behind any key that has no row. PATCH writes only the keys that changed, in one
    transaction. `workEnd` must come after `workStart`, checked against the stored value when only
    one of them is sent (`INVALID_WORK_HOURS`).
  - `POST /settings/school/logo` takes a multipart `file`. The file must be png, jpg or svg and both the
    declared type and the real bytes must match, otherwise 400 `INVALID_FILE_TYPE`. Over 2 MB is
    refused while it uploads with 413 `FILE_TOO_LARGE`. The file is saved under
    `UPLOADS_DIR/logo/logo-<uuid>.<ext>` and `school.logoUrl` changes, with a history row.
  - `GET /files/logo/:name` is `@Public()` (the sign-in page needs it). `GET /files/:folder/:name`
    needs a session. File names are checked against a strict pattern, so there is no path traversal.
    Files are served with CSP `sandbox` and `nosniff`, so an SVG can't run script.
  - `GET /settings/history?page&limit` returns changes newest first, paginated, with `meta`.
  - `SettingsHistoryListener` listens for `settings.changed`. It writes ONE `SettingChange` row per
    event for every scope (school, hr, lists, catalogue), mapping the scope to the DB enum by
    upper-casing it. It ignores unknown scopes. It logs failures and never throws, because the
    emitter's write has already committed.
  - Exported from `index.ts`: `SettingsService` (`getValues(keys)` and `setValues(scope, values, userId)`,
    which handle the diff, the transaction and the after-commit event) and `FileStorageService`.
- `core/school-structure`
  - `GET /stages?includeHidden`, `POST /stages`, `PATCH /stages/:id`. There is no DELETE: a stage is
    hidden with `isActive: false`, even while employees use it. Without a `sortOrder`, a new stage
    goes last. Each create or change emits `settings.changed`, scope `lists`, key
    `lists.stages.<id>`, with the old and new stage.
  - Exported: `StagesService` (`getActiveById` returns 404 or 400 `LIST_ITEM_HIDDEN`; also
    `getById` and `list`), plus `CreateListItemDto`, `UpdateListItemDto` and `ListItemsQueryDto`,
    which HR's departments and job titles can reuse.

## Schema change

New migration `20261117120000_setting_scope_lists_catalogue` adds `LISTS` and `CATALOGUE` to
`SettingScope` (`ADD VALUE IF NOT EXISTS`). History rows from lists and catalogue edits keep their
real scope instead of being folded into `HR`. `SettingScope` in shared got the same values.

## Edge cases (8/8 planned, plus extras)

All in `apps/api/test/core-settings.e2e-spec.ts`, each named after its case:
workEnd before workStart → 400, nothing saved · unknown key → 400 · one history row per change, with
old and new value and the user · logo wrong type → 400 / over 2 MB → 413 / valid → URL served ·
stage missing a name → 400 · hide a stage that is in use → allowed, no delete route · fresh-database
defaults · invalid language, workingDays or time → 400.
Extras: an emitted HR `settings.changed` produces a history row · the logo is public and other
`/files` need a session (T2's case, tested with the anonymous header) · an SVG is served with a
sandbox CSP · the history limit is capped · unknown or malformed stage id · full flow.
Unit tests: `settings.pure.spec.ts`, `settings.service.spec.ts`,
`settings-history.listener.spec.ts`, `stages.service.spec.ts`, and the interceptor's
file-passthrough case.

## Module-rule fix to T6's HR settings

HR's `HrSettingsRepository` wrote core's `SchoolSetting` table directly. It is removed.
`HrSettingsService` now reads with `SettingsService.getValues` and writes with
`SettingsService.setValues('hr', changed, userId)`, and `HrModule` imports `SettingsModule`. The
public methods and the `/hr/settings` behaviour are unchanged. Core writes all the changed keys in
one transaction, then emits one `settings.changed` per key (`emitAsync`, after the commit). The
listener is the only place history is written, so each change gets exactly ONE history row. T6's
`hr-settings` e2e test now checks this.

## Doubts

- The history key for stage edits (`lists.stages.<id>`, old and new = the whole stage) is our own
  choice. The contract only fixes the response shape.
- A hidden stage passed to `getActiveById` returns 400 `LIST_ITEM_HIDDEN`, not 409. This is a guess.
- `logoUrl` is a relative path (`/files/logo/…`). The web app has to prefix the API origin.
