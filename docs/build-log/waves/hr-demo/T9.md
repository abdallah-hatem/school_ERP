# T9 — Payroll and dashboard backend

Branch `feature/t9-payroll` from `6f9132c`, rebased on `origin/dev` (`2b18c3d`, with T8b, T11 and T13). Class: logic.

## Built

- `apps/api/src/modules/hr/payroll/`
  - `PayrollRunsController` provides `GET /hr/payroll-runs` (paginated, with totals),
    `POST /hr/payroll-runs`, `GET /hr/payroll-runs/:id` (`?search&departmentId&flagged`; the
    filters apply to the lines, and the totals always cover the whole run),
    `POST :id/recalculate`, `POST :id/approve`, `GET :id/bank-sheet` (.xlsx),
    `GET :id/lines/:lineId` (the payslip), `POST :id/adjustments` and
    `DELETE :id/adjustments/:adjId`. There is no DELETE route for runs.
  - `PayrollService` does the work:
    - Create: one DRAFT line per ACTIVE employee. A second run for the same month gets 409
      `PAYROLL_RUN_EXISTS`, and a race between two creates is settled by the unique month.
    - Recalculate: rebuilds every line from the current employees, penalties, lateness,
      adjustments and settings. Employees who have left are removed and new ones are added.
      Lines are upserted by employee, so a line keeps its id.
    - Approve: returns 409 `PENDING_PENALTIES` while any penalty dated in the month is pending.
      Otherwise it recalculates the lines and sets the run to APPROVED in one transaction, then
      emits `payroll.approved` after the commit.
    - Adjustments: draft runs only. A line must exist for the employee (400
      `EMPLOYEE_NOT_IN_RUN`). Adding or deleting one updates only that line's adjustment sums,
      net and flags.
    - Payslip and bank sheet: APPROVED runs only (409 `PAYROLL_NOT_APPROVED`).
    - Any write to an approved run gets 409 `PAYROLL_APPROVED`.
  - `PayrollRunsRepository` handles concurrency. Every write runs in a transaction that first
    claims the run row with `updateMany where status = DRAFT`. Writes to the same run therefore
    happen one at a time, and nothing is written once the run is approved.
  - `bank-sheet.ts` builds the sheet with exceljs 4.4.0. Columns are code, English name, Arabic
    name, national ID (stored as text, empty cell when missing) and net in EGP (`net / 100`,
    format `0.00`). Headers follow `Accept-Language`. Arabic sheets are right-to-left.
- `apps/api/src/modules/hr/dashboard/` serves `GET /hr/dashboard`. It returns the ACTIVE
  headcount, total and per stage, plus `currentRun` (this month's run with its net, or null) and
  this month's pending and approved penalties, counted by violation date.
- Registered in `hr.module.ts`. The change is additive and nothing new is exported.

## Doubts

1. **Approve recalculates.** Approving rebuilds the lines from current data before it locks the
   run. Without this, a penalty approved or cancelled after the last recalculation would leave the
   line out of step with the payslip's itemised penalties. The cost is that a settings change
   made after the last recalculation also lands at approval. If the owner wants approve to freeze
   exactly what was last shown, change approve to refuse a stale run instead.
2. **Payslip penalty amounts are shares.** Each itemised amount is
   `round(days ÷ line days × line penaltyAmount)`, taken from the line snapshot. That way a later
   divisor change can't alter an approved payslip; the run doesn't store its divisor. Because each
   share is rounded, the items can differ from the line total by a piastre.
3. **The payslip lists every APPROVED penalty in the month.** Notices and warnings appear too,
   with amount 0, so the payslip shows the full record. Say if only deducting penalties should be
   listed.
4. **What adjustments return and what the totals cover.** `POST adjustments` returns 201 with the
   run. The totals on `GET :id` always cover the whole run, whatever filters are applied.
5. **Orphaned adjustments.** An adjustment whose employee was deactivated stays stored and listed
   in `adjustments[]`, but no line counts it. It counts again if the employee is reactivated
   before approval.
6. **Edits outside this module's folders.** I edited `employees` and `penalties` (methods added,
   nothing else changed). Prettier also re-wrapped two existing lines in
   `penalty-records.service.ts`.
