# Spec — Audit log (core module)

Status: **approved by the owner** (2026-11-17), layout **option B — timeline by day** picked from
`design/mockups/audit-log.html`. Feature mode, guided.

## Why

A school's payroll needs a trustworthy answer to "who changed this, and when?". Today only settings
keep a history; employee edits, lateness, penalties' approval trail beyond the last person, payroll
runs and sign-ins leave no trace.

## What it is

One **append-only** record of every action that changes data or access, written by every module
through core. Two ways to read it: an **Activity** page for the whole system, and a **History** view
on a single record (employee, payroll run, penalty).

Not the same thing as **app logging** (requests, errors, stack traces for developers): that is
infrastructure in `apps/api/src/common/logging`, planned with hosting, and out of this spec.

## Decisions (recommended defaults — change any before approval)

| # | Decision | Why |
|---|---|---|
| D1 | `core/audit` module; every module records through core's exported `AuditService`. | Core is at the bottom of the module order, so every module may call it. One table, one screen. |
| D2 | The entry is written **in the same transaction** as the change. | An audit trail that can miss actions is worse than none. Today's settings history is written after the commit (a GUESS in §7) — this replaces it. |
| D3 | Transactions move to a request-scoped transaction context (`@nestjs-cls/transactional` with the Prisma adapter), so a service can wrap "change + audit" in one transaction without passing `tx` through every repository. | Today repositories open their own transactions; services can't join them. This is the standard Nest tool for it. |
| D4 | Who, when, IP and user agent are filled in by core from the request — callers pass only action, record, before and after. | Nobody can forget or fake the actor. |
| D5 | Actions are typed keys in `packages/shared` (`hr.employee.update`, `hr.payroll.approve`, `core.auth.sign_in_failed` …), each with an English and Arabic sentence template. Stored entries hold the key and the values, never a translated sentence. | Both languages render every entry; a typo fails typecheck. |
| D6 | **Every write endpoint declares its audit**: `@Audited('<action>')`, or `@NotAudited('<reason>')`. A test scans all controllers and fails CI when a POST / PATCH / PUT / DELETE handler has neither. | New modules can't ship unaudited writes. |
| D6b | `@Audited` also checks at run time: if the handler succeeds but recorded no entry with that action in its transaction, the request fails and the change rolls back. | A declaration without the actual `audit.record()` call breaks in the module's own tests, never silently in production. |
| D7 | Changes store **only the changed fields**, each with before and after. Secrets (password hashes, tokens) are never stored; money is stored in piastres and shown formatted. | Small entries, readable diffs, no leaks. |
| D8 | Append-only, enforced in the database: a trigger rejects `UPDATE` and `DELETE` on `audit_entries`. Kept forever for now. | Nobody, including the app, can rewrite history. Retention can become a setting later. |
| D9 | Settings history **moves into** the audit log: existing `setting_changes` rows are copied in by a migration; the Settings → Change history section reads the audit log filtered to settings. `setting_changes` is dropped after the copy is verified. | One system, not two. |
| D10 | Who can see it: the **HR admin** (the only role today). When roles land, a permission `core.audit.view` (all) and per-record history follows the record's own view permission. **P4 (roles spec):** Activity, its day totals, people picker and "Today at a glance" count only entries about records in the viewer's scope (employees, penalties, lateness and payroll per employee); a History outside it is 404; salary-type values are hidden (`hidden: true`) without the salary key at scope `all`, payroll-run totals shown with `hr.payroll.view` at `all`. | Matches §2; ready for roles. |
| D11 | Sign-in, sign-out and **failed** sign-ins are recorded (failed ones with the email typed, never the password). | Security baseline; pairs with login rate limiting in Next up. |

## What gets recorded in v1

| Module | Actions |
|---|---|
| Core — auth | sign in, sign out, failed sign-in |
| Core — settings | school settings change, logo change, stage add / edit |
| HR — employees | create, edit (changed fields), deactivate, reactivate |
| HR — lists | department / job title add, edit |
| HR — rules | HR settings change, penalty group / violation add, edit |
| HR — penalties | record, approve, cancel |
| HR — lateness | month saved (per employee: minutes before → after) |
| HR — payroll | run created, recalculated, approved; adjustment added, removed |

Reads are not recorded (no "viewed payslip") in v1.

## Screens

- **Activity** (core, sidebar → Administration → Activity): newest first, server-paged, 10 per page.
  Filters: person, module, action, date range, and a search for the record (employee name or code,
  payroll month). Each entry: who, a sentence, module, time; expands to a field / before / after
  table.
- **History** on the employee profile and the payroll run page: the same entries for that record.
- **Settings → Change history**: unchanged for the user, now reading the audit log.

Layout: **option B — timeline by day** (`design/mockups/audit-log.html`, tab B), picked by the owner:
entries read as sentences under day headers, the first changed fields shown inline (+ "n more"),
filters in a side panel (date range, module switch, action-type chips, searchable person picker,
"today at a glance" counts). On phone the filters sit behind one button. The profile's **History**
tab is the same timeline grouped by month, with field and person filters. Settings moves into a new
**Administration** sidebar group together with **Activity**.

## API (contract)

- `GET /audit?page&limit&actorId&module&action&from&to&q` → `Paginated<AuditEntry>`
- `GET /audit/records/:entityType/:entityId?page&limit` → `Paginated<AuditEntry>`
- `AuditEntry`: `id, action, module, entityType, entityId, entityLabel, actor {id, name} | null,
  changes: {field, before, after}[], meta {ip, userAgent}, at`.
- No write endpoints: entries are only written by modules through `AuditService`.

## Data

`audit_entries`: `id`, `action`, `module`, `entity_type`, `entity_id`, `entity_label` (snapshot, e.g.
the employee's name at the time), `actor_id` (null for failed sign-ins / system), `changes` (jsonb),
`meta` (jsonb: ip, user agent, request id), `at`. Indexes: `at desc`; `(entity_type, entity_id, at)`;
`(actor_id, at)`; `(module, at)`.

## Edge cases (with expected outcome)

1. The change fails or rolls back → no audit entry (same transaction). — D2
2. The audit write fails → the change rolls back and the user sees an error. — D2
3. Saving a form with nothing changed → no entry. — D7
4. A user is later deleted or renamed → old entries still show who it was (name snapshot). — Data
5. Failed sign-in for an unknown email → entry with that email, no actor. — D11
6. Payroll approval recalculates lines → one entry "approved" with totals, not one per line. — v1 table
7. Lateness month saved with 40 rows changed → one entry with the changed employees' before/after. — v1 table
8. Someone tries `UPDATE`/`DELETE` on `audit_entries` directly → the database refuses. — D8
9. A new write endpoint without `@Audited`/`@NotAudited` → CI fails. — D6
10. Arabic UI → every entry reads in Arabic, including old ones. — D5
11. Old settings history → visible exactly as before after the migration (same count, values, people, times). — D9
