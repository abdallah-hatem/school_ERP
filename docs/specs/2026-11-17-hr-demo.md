# Spec — Foundation + HR demo (2026-11-17)

Status: **awaiting approval.** Business rules live in `docs/BUSINESS_LOGIC.md` (§ references below).

## Goal

A real, thin first version for the client demo on **Sunday 2026-11-22**, run locally:

1. **Foundation:** the app shell every later module builds on.
2. **HR:** employees, penalties, monthly lateness, and a monthly payroll run.
3. **Settings:** show that the school's rules are data, not code. Change a rule, rerun payroll, and
   the numbers change.

Source of requirements: the HR department's scope page and the staff internal regulations (25
scanned pages, received 2026-11-16). They describe attendance, leave, permissions, contracts and a
large penalty catalogue. **They do not define salary calculation**, so payroll is basic salary minus
deductions (owner's decision, 2026-11-17).

## Intake decisions

## Users and roles

- **HR admin** — signs in, manages employees, records penalties and lateness, runs and approves
  payroll, edits settings. Seeded account in `CREDENTIALS.local.md`.

## Entities

Departments · Stages · Job titles · Employees · Penalty catalogue (violations with levels) ·
Penalty records · Monthly lateness entries · Payroll adjustments · Payroll runs and lines ·
Settings · Users. Rules for each are in §3–§7.

## Flows

1. **Sign in** → dashboard (headcount, this month's payroll status, penalties this month).
2. **Employees:** list (search, filter by department, stage, status) → add / edit → profile
   (details, penalties history, payroll history) → deactivate.
3. **Record a penalty:** pick an employee and a violation from the catalogue, plus a date → the
   system shows the repeat level and the action it implies → save as pending → approve or cancel
   with a reason (§4).
4. **Monthly lateness:** for a month, enter each employee's accumulated late / early-leave minutes
   (manual now; fingerprint import later) → the system shows the days deducted (§5).
5. **Payroll:** create the month's run → lines calculated for every active employee → add one-off
   adjustments → recalculate → approve (locks the month) → payslip (print, EN/AR) and bank sheet
   (Excel) (§6).
6. **Settings:** school identity; lateness rule; payroll rule (day divisor, part-time percentages);
   penalty catalogue and repetition window; lists (departments, stages, job titles) (§7).

## The demo story (what Sunday shows)

1. Arabic ↔ English, the whole app flips.
2. Employees list and a profile.
3. Record a repeated violation. The level goes up automatically from the catalogue.
4. Run November payroll. Show the deductions from penalties and lateness.
5. In Settings, change the lateness rule, the day divisor or a part-time percentage → recalculate →
   the numbers change. (A catalogue edit changes pending penalties and new ones, never approved ones.)
6. Approve → print a payslip in Arabic → export the bank sheet.
7. Show it on a phone: the same screens, responsive.

## Out of scope for the demo (Planned, in §8)

Leave, permissions and the employee request portal · fingerprint device integration · recruitment
and job applications · contracts and renewal deadlines · medical and legal workflows · the annual
raise · tax and social insurance · roles and permissions beyond HR admin · reports beyond payroll ·
notifications · hosting.

## Contract (stage 3, 2026-11-17)

Every response uses the house envelope (`building-backends` → response-envelope):
`{ success, message, statusCode, data?, error?, timestamp, path?, meta? }`. Lists are paginated:
`?page=1&limit=10&search=` (default limit 10 — owner 2026-11-17; max 100) and return `meta { total, page, limit, hasNextPage,
hasPreviousPage }`. Errors carry a stable code in `error` (e.g. `PAYROLL_APPROVED`) and a translated
`message` (EN/AR via `Accept-Language` only — a `lang` cookie never changes it; the web app sends
the page's `[locale]`). Ids are UUIDs. Dates are `YYYY-MM-DD`; months are `YYYY-MM`.
**Money is integer piastres** in the API (`basicSalary: 1400000` = EGP 14,000.00); the frontend
formats it. Day counts are decimals in steps of 0.25 (`1.25`). All routes need a signed-in user
(JWT in httpOnly cookies) except `POST /auth/login` and `POST /auth/refresh`. Names come in pairs:
`nameEn`, `nameAr`.

Shared types, enums, permission and setting keys live in `packages/shared`.

### Auth — `core/auth`
| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/auth/login` | `{ email, password }` | `{ user }`; sets access + refresh cookies |
| POST | `/auth/refresh` | — (refresh cookie) | `{ user }`; rotates cookies |
| POST | `/auth/logout` | — | `{}`; clears cookies |
| GET | `/auth/me` | — | `{ id, email, name, role }` |

### School settings — `core/settings`
| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/settings/school` | — | `{ nameEn, nameAr, logoUrl, defaultLanguage, workStart, workEnd, workingDays[] }` |
| GET | `/settings/school/public` | — (**public**, no session) | `{ nameEn, nameAr, logoUrl, defaultLanguage }` for the sign-in page |
| PATCH | `/settings/school` | any subset of the above (no `logoUrl`) | the updated object; `workStart` / `workEnd` must be `HH:mm` on a 30-minute boundary (`07:30` yes, `07:15` → 400 `VALIDATION_FAILED`) |
| POST | `/settings/school/logo` | multipart `file` (png/jpg/svg, ≤ 2 MB) | `{ logoUrl }` |
| GET | `/settings/history` | `?page&limit` | change list `{ key, oldValue, newValue, changedBy, changedAt }` |

### School structure — `core/school-structure`
| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/stages` | `?includeHidden` | `[{ id, nameEn, nameAr, sortOrder, isActive }]` |
| POST | `/stages` | `{ nameEn, nameAr, sortOrder? }` | stage |
| PATCH | `/stages/:id` | `{ nameEn?, nameAr?, sortOrder?, isActive? }` | stage |

### HR lists — `hr`
Same shape as stages for `/hr/departments`, `/hr/job-titles` and `/hr/employee-grades` (GET, POST, PATCH :id; added 2026-11-24 — an employee's `employeeGradeId`, returned as `employeeGrade: { id, nameEn, nameAr } | null`). No DELETE:
items in use are hidden (`isActive: false`). Job titles also carry `managesPeople` (boolean,
default `false`; POST / PATCH accept it) — §3 "Direct managers" (2026-11-18).

### Employees — `hr`
| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/hr/employees` | `?page&limit&search&departmentId&stageId&status&workSystem&managesPeople&excludeId` | paginated employee summaries `{ id, code, nameEn, nameAr, department, stage, jobTitle, workSystem, basicSalary, status }` — `managesPeople=true` keeps only employees whose job title manages people, `excludeId` leaves one employee out (the direct-manager picker) |
| GET | `/hr/employees/:id` | — | full employee (all §3 fields, with department / stage / job title / manager objects) |
| GET | `/hr/employees/:id/payroll-lines` | `?page&limit` | paginated `{ runId, lineId, month, status, net }` — the employee's line in each run, newest month first, `net` from the line snapshot; 404 for an unknown employee (T19) |
| POST | `/hr/employees` | `CreateEmployeeDto` (all §3 fields except `code`, `status`) | employee (code assigned) |
| PATCH | `/hr/employees/:id` | partial `CreateEmployeeDto` | employee — a new `managerId` whose job title doesn't manage people → 400 `MANAGER_NOT_MANAGING` (the existing manager unchanged is kept) |
| POST | `/hr/employees/:id/deactivate` | — | employee |
| POST | `/hr/employees/:id/reactivate` | — | employee |

`workSystem`: `FULL_TIME` · `PART_TIME_4` · `PART_TIME_3` · `PART_TIME_2`.
`gender`: `MALE` · `FEMALE`. `status`: `ACTIVE` · `INACTIVE`.

### Penalty catalogue — `hr`
| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/hr/penalty-groups` | — | `[{ id, nameEn, nameAr, sortOrder, violations: [{ id, nameEn, nameAr, note, isActive, levels: [{ level, action, days }] }] }]` |
| POST | `/hr/penalty-groups/:groupId/violations` | `{ nameEn, nameAr, note?, levels[] }` | violation |
| PATCH | `/hr/violations/:id` | `{ nameEn?, nameAr?, note?, isActive?, levels? }` | violation |
| POST | `/hr/penalty-groups` | `{ nameEn, nameAr, sortOrder? }` | group |
| PATCH | `/hr/penalty-groups/:id` | `{ nameEn?, nameAr?, sortOrder?, isActive? }` | group |

`action`: `NOTICE` · `WARNING` · `DEDUCT_DAYS` · `INVESTIGATION` (may have `days`) ·
`RAISE_HALF_LOSS` · `RAISE_LOSS` · `RAISE_DEFER_3M` · `PAY_CUT` · `DEMOTION` · `DISMISSAL`.
`days` is required and `> 0` when the action is `DEDUCT_DAYS`, optional for `INVESTIGATION`, absent
otherwise. `levels` is 1–5 entries numbered 1..n with no gaps.

### Penalty records — `hr`
| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/hr/penalties` | `?page&limit&employeeId&month&status` | paginated records |
| GET | `/hr/penalties/preview` | `?employeeId&violationId&date` | `{ level, action, days, priorCount }` (nothing saved) |
| POST | `/hr/penalties` | `{ employeeId, violationId, date, note? }` | record (`PENDING`, level and action computed) |
| POST | `/hr/penalties/:id/approve` | — | record (`APPROVED`; level and action fixed now) |
| POST | `/hr/penalties/:id/cancel` | `{ reason }` | record (`CANCELLED`) |

### Monthly lateness — `hr`
| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/hr/lateness?month=YYYY-MM` | — | `{ locked, rule: { graceMinutes, steps, extraHourDays }, rows: [{ employee, department: { id, nameEn, nameAr }, minutes, days }] }` for active employees (0 when not entered); `locked` is true once the month's payroll is approved; `rule` is the lateness rule the days use (§5, readable without `hr.settings.view`) |
| PUT | `/hr/lateness/:month` | `{ entries: [{ employeeId, minutes }] }` | the month's list (same shape as GET), with `days` computed |

### HR rule settings — `hr`
| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/hr/settings` | — | `{ lateness: { graceMinutes, steps: [{ hour, days }], extraHourDays }, payroll: { dayDivisor, partTime: { PART_TIME_4, PART_TIME_3, PART_TIME_2 } }, penalties: { repetitionWindow } }` |
| PATCH | `/hr/settings` | any subset | the updated object |

### Payroll — `hr`
| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/hr/payroll-runs` | `?page&limit` | runs `{ id, month, status, totals, approvedAt }` |
| POST | `/hr/payroll-runs` | `{ month }` | run (`DRAFT`, lines calculated) — 409 if the month exists |
| GET | `/hr/payroll-runs/:id` | `?search&departmentId&flagged` | run with `totals`, `lines[]`, `pendingPenalties` (live count of PENDING penalties dated in the month; 0 once approved) and `rules` (today's HR rules: `{ lateness, payroll: { dayDivisor, partTime }, penalties: { repetitionWindow } }`, readable without `hr.settings.view`; every write returning the run carries them too) |
| POST | `/hr/payroll-runs/:id/recalculate` | — | run |
| POST | `/hr/payroll-runs/:id/approve` | — | run (`APPROVED`) |
| GET | `/hr/payroll-runs/:id/bank-sheet` | — | `.xlsx` file (approved runs only) |
| GET | `/hr/payroll-runs/:id/lines/:lineId` | — | payslip data |
| POST | `/hr/payroll-runs/:id/adjustments` | `{ employeeId, type: ADDITION \| DEDUCTION, amount, reason }` | run (draft only) |
| DELETE | `/hr/payroll-runs/:id/adjustments/:adjId` | — | run (draft only) |

Line (employee fields are a **snapshot** taken at calculation): `{ id, employeeId, employeeCode,
nameEn, nameAr, nationalId, departmentId, departmentNameEn, departmentNameAr, basicSalary, workSystem, monthSalary, dayValue, penaltyDays,
penaltyAmount, latenessMinutes, latenessDays, latenessAmount, adjustmentAdditions,
adjustmentDeductions, net, flags[] }`.
Adjustment (in the run's `adjustments[]`): `{ id, employeeId, employeeCode, nameEn, nameAr, type,
amount, reason, createdAt, applied }` — `applied` is false when the employee has no line in the run
(left before the last recalculate), whatever the line filters (T19).
Totals: `{ employees, monthSalary, penaltyAmount, latenessAmount, adjustmentAdditions,
adjustmentDeductions, net, flagged }`. Flags: `NET_FLOORED` · `PENDING_PENALTIES`.

Payslip (`GET /hr/payroll-runs/:id/lines/:lineId`, approved runs only, 409 on a draft): the line plus
`penalties: [{ date, violationNameEn, violationNameAr, level, action, days, amount }]`,
`adjustments: [{ type, amount, reason }]`, `school: { nameEn, nameAr, logoUrl }`, `month`.

The logo under `/files/…` is public (the sign-in page shows it); every other file needs a session.
